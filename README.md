# Energy Disaggregation (NILM)

A smart meter sees one number: total household power. But the interesting
questions are per-appliance — how much does the HVAC cost, is the fridge
cycling normally? Non-intrusive load monitoring answers that from the
aggregate alone. I built an ML disaggregator that separates a meter reading
into per-appliance traces, the kind of analysis I'd want running on the
telemetry of the IoT devices I used to test.

## Approach
1. **Synthetic meter data** (`src/generate_data.py`): 1-minute resolution, 14
   days. Four appliances with distinct behaviors — fridge (periodic compressor
   cycles), HVAC (thermostat-driven on outdoor temperature), washer (rare
   45-min high-power blocks with a spin spike), TV (evening use) — plus base
   load. Per-appliance columns are ground truth; the model only sees the
   aggregate.
2. **Features**: aggregate power, time-of-day (sin/cos), day of week, and
   rolling mean/std/max over 15- and 60-minute windows.
3. **Model**: one RandomForestRegressor per appliance — except the washer.
   The washer runs ~1% of the time, and per-minute regression simply couldn't
   see it (energy error 72%). So the washer gets event detection instead: a
   balanced on/off classifier plus the typical running power. Two-stage
   modeling for rare events is standard practice in the NILM literature.

## Results (last 4 days held out)
| Appliance | MAE (W) | Baseline MAE (W) | Energy error |
|---|---|---|---|
| Fridge | 6.9 | 72.8 | 0.6% |
| HVAC | 4.0 | 973.4 | 0.0% |
| Washer | 1.9 | 23.4 | 13.5% |
| TV | 3.9 | 25.9 | 0.9% |

(Baseline = always predict the appliance's mean power.) The patterned
appliances disaggregate almost perfectly; the washer is the known-hard case —
infrequent, high-power appliances are the classic NILM challenge — and the
two-stage fix cut its energy error from 72% to 13.5%.

## Project structure
```
├── src/
│   ├── generate_data.py   # synthetic meter + appliance ground truth
│   ├── disaggregate.py    # per-appliance models (regression + washer event detection)
│   └── evaluate.py        # metrics vs baseline + sample-day plot
├── requirements.txt
└── README.md
```
`data/` and `figures/` are generated by the scripts and git-ignored.

## How to run
```bash
pip install -r requirements.txt
python src/generate_data.py   # data/energy.csv
python src/disaggregate.py    # data/predictions.csv
python src/evaluate.py        # metrics + figures/sample_day.png
```

## Design decisions
- **Why per-appliance models instead of one multi-output model:** appliances
  have unrelated physics (thermostat vs. timer vs. human behavior); separate
  models let each learn its own pattern and make failures easy to diagnose.
- **Why the washer is special-cased:** I tried plain regression first and
  reported its failure honestly (72% energy error) before fixing it — the
  two-stage approach is the actual lesson, not a trick.
- **Why energy error matters most:** for billing and efficiency use-cases, the
  total kWh per appliance matters more than per-minute accuracy; I report both.
- **Synthetic but principled:** the appliance signatures (duty cycles, setpoint
  hysteresis, spin spikes) mirror real load profiles, so the modeling lessons
  transfer to real meter data.
